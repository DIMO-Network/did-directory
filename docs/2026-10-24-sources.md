# Sources: who may write about a vehicle

Status: draft, 2026-10-24, branch `sources` (off `identity-scopes`).

This replaces din's "connection" (the connection license NFT and the mTLS
certificate dis checks) with ordinary parties in the delegation model. It is
the "what replaces the din connection concept" punt from 2026-09-21.

## Model

An event about a vehicle names three parties, in the CloudEvent header DIMO
already uses:

| attribute  | who | identity |
|------------|-----|----------|
| `subject`  | the vehicle V | its DID |
| `source`   | the relay that sent it in (Flespi, a Ruptela server, an OEM bridge) | a directory DID with a `#signing` key |
| `producer` | the machine that took the reading | its DID if it has one, otherwise an identifier the source assigns (IMEI, serial) |

Agreed 2026-10-24:

1. **V's controller (or anyone who may grant for V) grants write to the
   source.** It is a delegation with `telemetry:write` (or another `*:write`)
   covering V, `to` the source's DID. There is no separate connection or
   pairing record type, and the grant does not name a machine.
2. **The source labels each event with its producer.** The store takes the
   source's word for which machine it was; the source is the party trusted
   with the grant.
3. **Both may sign.** The source always signs. A machine may sign too, and a
   machine that signs has a DID. A `did:key` is enough: a machine needs no
   directory entry.
4. **Signatures are kept** with the event, so a reader can check them later,
   not just the ingest service.
5. The attribute and the role are called **source**. "Relay" is fine in prose.
   Not "oracle", not "connection".

The machine's signature is evidence of where the data came from. It does not
authorize anything: the write is allowed because the source holds a grant.
The store therefore never needs to know about machines to accept data.

## Signatures (built: `pkg/provenance`)

Both signatures cover the same signing input: a version line, then one
`name=value` line each for `id`, `source`, `producer`, `subject`, `type`,
`time` (RFC 3339, UTC), `dataversion`, `datacontenttype`, and
`data=sha256:<hex>` of the exact data bytes. A signature over the data alone
(today's `signature` attribute) would let a signed reading be replayed under
another car, time or machine; this one cannot.

Each signature is a compact JWS with a detached payload, `header..signature`,
whose header carries `alg` (ES256 or ES256K, which must match the key) and
`kid`. They travel as the CloudEvent extensions `sourcesignature` and
`producersignature`.

Rules `provenance.Verify` enforces:

- The source signature is required, and its `kid` must be a key of `source`.
- If `producer` is a DID other than `source`, the producer signature is
  required, with a key of that DID. Otherwise a source could attribute data to
  a machine DID just by writing it in the header.
- A producer signature on a producer that is not a DID is refused.
- If `producer == source`, the relay produced the data itself and signs once.

## Write path

Decided 2026-10-24: **a source sends to din under its own identity token**, not
an access token per car. A relay that sends for thousands of cars signs in
once (DID sign-in at dauth, `aud` = din, scope `write`, DPoP-bound to its
`#signing` key, decision 31) and does no exchanges. The machines behind it
never talk to dauth at all.

What din does with a batch:

1. Check the identity token and its DPoP proof, as the org host does.
2. For each event: `source` must be the token's subject, and
   `provenance.Verify` must pass.
3. Check that `source` may write about `subject` now, by calling the org host's
   `POST /authorize` with `anyGrant: true`, caller = source, vehicle =
   subject, abilities = the write ability for `type`. Cache the answer per
   (source, vehicle) for a short TTL. din is a configured issuer on the host.
4. Store the event with both signatures, the exact data bytes, the time it
   arrived, and the grant URI the answer's chain names first, so it is on
   record which grant let it in.

`anyGrant` (built) means the host finds the authority itself. It tries the
caller as controller, then every delegation on this host to the caller or to
an org that gave the caller a role. The first one covering the vehicle with
every ability asked for answers. If none does, the refusal is
`exclusive_hold` if somebody holds the car, else `not_covered`: one grant
among many being revoked says nothing useful. A relay can therefore be a bare
DID, or an org whose ingest servers are members with a role carrying the write
ability.

Still open:

- **Cost of the lookup.** `anyGrant` evaluates every grant the source holds
  until one covers the car. That is fine for tens of grants, and a relay with
  10,000 single-car grants needs an index by (assignee, vehicle) on the host.
  Tag grants (a whole fleet to one relay) keep the count small and are the
  shape to encourage.
- **Grants on other hosts.** `Assigned` only sees this host. A car whose
  controller's repository is elsewhere needs din to know which host to ask
  (from the vehicle's DID document) or a federation step.
- **dauth audience.** Sign-in may only ask for the exchange or the org host
  today, so din needs adding as an allowed audience.
- **Arrival time, decided 2026-10-25.** A write is checked when it arrives:
  the grant must be live then, which is what `ClassOf` already does for
  `*:write`. The event's `time` is not checked against the grant. The source
  sets it and could fudge it, so a check on it would protect less than it
  seems to. The consequences are accepted: a backlog that arrives after the
  grant ends is refused, and a reading stamped before the grant began is
  taken. din records when each event arrived next to the claimed `time`, so
  backdating can be seen afterwards.
- **Reads by provenance** (the machine's maker reading what its devices sent)
  is set aside for now.
- **Key rotation.** `DIDKeys` resolves a directory DID's current document. To
  check an old signature after the source rotates `#signing`, you need the key
  as of the event (the directory has the audit log to answer that). Machine
  `did:key`s never rotate.
- **Storage.** The `cloudevent` library and dq's raw events keep one
  `signature` column over data only. They need the two extension columns, and
  the exact data bytes must survive storage. Re-encoded JSON breaks the hash.
- **Which ability per event type.** `telemetry:write` for `dimo.status`;
  attestations, fingerprints and so on probably need their own `*:write`.
